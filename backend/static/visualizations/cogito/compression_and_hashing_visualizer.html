Compression & Hashing, Made Visible

Five verified demos: build a Huffman tree by hand, watch run-length encoding win and lose, find LZ77's repeated substrings, drop keys into hash-table buckets, and watch one changed character scramble a hash completely.

Building the Optimal Prefix Code

What's happening: type any text. Its letter frequencies get counted, a Huffman tree gets built by repeatedly merging the two least-frequent nodes, and the resulting code's average length is compared against the entropy floor and fixed-length encoding.

Try this: start with the default "ABRACADABRA" and confirm the numbers match the tutorial exactly (23 bits vs. a 22.44-bit entropy floor). Then try a very lopsided text (like "AAAAAAAAAB") and watch the compression ratio climb even higher, since Huffman coding rewards skewed frequencies the most.

Why it matters: the tree assigns short codes to frequent letters and long codes to rare ones automatically — nobody has to guess which letters deserve short codes, the merge order forces it.

When Repetition Pays Off — and When It Doesn't

What's happening: type any text of repeated characters. Each run of the same character becomes one "character + count" pair.

Try this: start with the default (a 2x win) then clear it and type "ABCDEFGHIJ" — watch the ratio flip below 1.0, proving RLE can make data *larger* when there's nothing to repeat.

Why it matters: RLE makes a bet — that runs exist — and the compression ratio directly measures how good that bet turned out to be for this specific input.

"Haven't I Seen This Before?"

What's happening: scanning left to right, every position checks whether the upcoming text exactly matches something already seen earlier. A match becomes a (distance, length) token instead of literal characters.

Try this: keep the default "the cat sat on the mat" and confirm two matches are found (matching the tutorial's distance=4/length=3 and distance=15/length=4). Then try a longer text with a repeated phrase to watch the compression ratio improve.

Why it matters: Huffman coding alone can never notice a repeated phrase — LZ77 is the piece of a real compressor that specifically hunts for exactly that.

Modular Arithmetic, Deciding Where Things Live

What's happening: each key is hashed with h(x) = x mod (table size) and dropped into its bucket. Buckets with more than one key (highlighted) are collisions, resolved by chaining.

Try this: keep the defaults and confirm bucket 5 collects three keys (12, 5, 19) and bucket 2 collects two (44, 23), exactly as in the tutorial. Then change the table size to a prime like 11 and watch the same keys spread out more evenly.

Why it matters: lookup speed in a real hash table depends entirely on collisions staying rare — a bad hash function or table size turns every lookup into a slow scan through one overstuffed bucket.

One Character Changed, Everything Changed

What's happening: both text boxes are hashed with the identical simple polynomial rolling hash. Edit either one by even a single character and watch the two hash values diverge completely, with no visible relationship between them.

Try this: keep the defaults ("hello" vs. "hollo") and confirm the hashes match the tutorial's 99,162,322 and 99,460,232. Then try changing only the capitalization of one letter and watch the hash change just as completely.

Why it matters: if a hash function's output only changed a little for a small input change, an attacker could search for collisions by making small, guided edits — the avalanche effect is precisely what removes that shortcut.
