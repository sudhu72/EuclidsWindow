The Body Around the Brain

A model predicts tokens; everything else — tools, MCP, skills, loops, memory, graphs of agents, multiple models, and the guardrails containing all of it — is engineered around it. Six pieces of that engineering, made interactive.

Each panel below reads top to bottom: what's happening, a try this, and why it matters.

Six Organs Around One Brain

What's happening: the model (center) only predicts tokens. Click any organ around it to see what it actually adds, and which Part of the tutorial builds it.

Try this: click through all six — notice that every single one is answering "the model can't do this on its own, so something has to be built around it to supply it."

Click an organ above.
Why it matters: "the model got smarter" and "the harness got better" are different claims — most of what separates a demo from a production agent is this diagram, not the model in the middle of it.

Client, Server, and Five Steps Between Them

What's happening: the harness (an MCP client) talks to an external MCP server in a standard sequence — discover, call, execute, return, append. Step through it.

Try this: step all the way through, then notice step 5 — the server's result doesn't magically appear in the model's head, it has to be explicitly appended to context, exactly like any other tool result.

Why it matters: a client that only ever discovers what a server currently offers, rather than hardcoding it, keeps working when the server adds or changes tools — the entire reason MCP is a discovery protocol, not just a shared function-call format.

Five Protocols, One Question Each: Who's Talking to Whom?

What's happening: click a protocol to see who it connects, its one distinguishing mechanic, and its real, current status (as of 2026) — not marketing copy.

Try this: click MCP, then A2A, and notice the diagram itself changes shape — MCP is always agent-to-tool (one arrow, asymmetric), every other protocol here is agent-to-agent (a two-way relationship between peers).

Why it matters: "just use a protocol" isn't one decision — agent-to-tool and agent-to-agent are structurally different problems, and even within agent-to-agent, centralized discovery (A2A) and fully decentralized trust (ANP) solve for different enemies.

Same Question, Same Facts, Two Retrieval Methods

What's happening: the identical two stored facts, searched two ways. Vector similarity picks whichever stored text scores highest against the query — with no notion of which fact is still true. Graph traversal follows the actual relationship and checks which edge is currently valid.

Try this: run "Vector similarity" first and notice it confidently returns the *wrong*, superseded answer — then run "Graph traversal" and watch it correctly follow Alice → team → current manager instead.

Query: "Who currently manages the team Alice is on?"
Pick a search method above.
Why it matters: both stored facts are genuinely, textually "about team management" — vector similarity has no built-in way to prefer the current one over the superseded one, because that's a fact about *time*, not meaning.

Same Work, Five Topologies, Five Very Different Totals

What's happening: pick a topology and adjust each node's cost (seconds). Watch the token move through the actual path taken, and the total latency recompute live.

Try this: load the default costs on Sequential (total 10s), then switch to Parallel with the exact same four costs (total drops to 4s) — nothing about the work changed, only the shape it's arranged in.

Why it matters: topology is a latency (and cost) decision, not a cosmetic one — defaulting to sequential when steps are independent is pure wasted time, paid on every single run.

Imperfect Layers, Stacked

What's happening: each ring is one guardrail layer, catching an attack independently at its own rate. The combined catch rate is what survives after every layer gets a chance.

Try this: set the per-layer rate to 60% and slide layers from 1 to 4 — the combined rate climbs 60% → 84% → 93.6% → 97.4%, without any single layer improving at all.
